# Prototype: render cache sizing

Issue #8 · Parity PRE-01 · ADR 0005 · Phase 1 – Risk Prototypes

## Question

ADR 0005 replaces the old `NSCache` (count limit 200, pages 0…200 on open, ±50 around each request) with an actor-based cache that renders the current and next page first, fills a neighborhood in the background and is limited by bytes, with a smaller budget on iPad. This prototype measures render time and image memory per page so the neighborhood size and the budgets can be set.

## What was tried

A Swift Testing suite (`RenderMeasurements`) in `SlidePilotRenderingTests`, run on macOS and in the iPad simulator. It is prototype code and is **not** in `main`; it stays on the local branch `prototype/render-cache-measurements` (see "Re-running" below).

- **Rendering path:** the way the production cache is expected to work. `PDFPage.draw(with: .mediaBox, to:)` into an 8-bit sRGB `CGContext` (BGRX, no alpha), white background, page aspect-fit into the target size, `makeImage()` → `CGImage`. Each render is wrapped in `autoreleasepool`.
- **Targets** (pixels; the page is fitted, so a 4:3 slide on a 16:9 screen uses 3/4 of the width):

  | Target | Fitted 4:3 image | Bytes per image |
  |---|---|---|
  | Thumbnail 200×150 pt @2x | 400×300 | 0.5 MiB |
  | Presenter "next" 600×450 pt @2x | 1200×900 | 4.1 MiB |
  | Presenter "current" 900×675 pt @2x | 1800×1350 | 9.3 MiB |
  | Full screen 1920×1080 | 1440×1080 | 5.9 MiB |
  | Full screen 2560×1440 | 1920×1440 | 10.5 MiB |
  | iPad Pro 13″ 2752×2064 | 2752×2064 | 21.7 MiB |
  | Full screen 3840×2160 (4K) | 2880×2160 | 23.7 MiB |
  | Full screen 5120×2880 (5K) | 3840×2880 | 42.2 MiB |
  | Full screen 6016×3384 (6K, Pro Display XDR) | 4512×3384 | 58.2 MiB |

  Memory is exactly `width × height × 4`; the split-notes deck (`notes-right.pdf`, 8:3 pages) is about the same bytes per image because it is fitted to the same box.
- **Documents:**
  - `Fixtures/large-deck.pdf` (320 text pages), `plain-slides.pdf` (formula, table, TikZ), `notes-right.pdf` (split notes).
  - A **synthetic heavy deck** generated by the test: every page has a 2400×1800 JPEG photo (DCT-encoded, like a photo in a real deck) and 2000 stroked Bézier curves. The fixtures are text only and render in a few milliseconds, so this deck gives an upper bound for image- and TikZ-heavy slides.
- **Measurements:** render time per page (first pass "cold", second pass "warm"; median, p95, max over up to 40 pages), task memory (`task_vm_info`: `phys_footprint`, `internal`, `compressed`, `resident_size`) while keeping 30 rendered images, the same with buffers the test owns, the effect of a missing autorelease pool, and the time to fill a 20-page neighborhood at 4K sequentially vs. with 4 tasks that each open their own `PDFDocument` (no `PDFPage` shared across threads, DEF-02).

**Environment:** Apple-silicon Mac, macOS 27.0.1, Xcode 27.2, Debug build (the time is spent in PDFKit/Core Graphics, which are release builds either way). iPad: simulator "iPad Pro 13-inch (M5)", iOS 27.2, on the same Mac. Single runs; the numbers are stable to roughly ±20 % between runs.

## Measurements

### Render time per page (warm median, p95 in brackets)

| Target | Text fixture, Mac | Text fixture, iPad sim | Heavy page, Mac | Heavy page, iPad sim |
|---|---|---|---|---|
| Thumbnail 400×300 | 0.1 ms | 2.6 ms | 16 ms | 23 ms |
| Presenter next 1200×900 | 0.4 ms | 2.8 ms | 50 ms | 67 ms |
| Presenter current 1800×1350 | 0.7 ms | 3.2 ms | 146 ms | 178 ms |
| 1920×1080 | 0.4 ms | 3.0 ms | 111 ms | 137 ms |
| 2560×1440 | 0.7 ms | 3.3 ms | 160 ms | 195 ms |
| iPad Pro 13″ 2752×2064 | 1.4 ms | 4.2 ms | 275 ms (293) | 344 ms (486) |
| 4K | 1.6 ms | 4.5 ms (15) | 294 ms (300) | 354 ms (361) |
| 5K | 2.8 ms | 6.0 ms | 494 ms (511) | 573 ms (583) |
| 6K | 3.9 ms | 7.3 ms | 674 ms (703) | 774 ms (785) |

- `plain-slides.pdf` (formula, table, TikZ) and `notes-right.pdf` behave like the text fixture: ≤ 2.6 ms at 4K, ≤ 7.7 ms at 6K on the Mac.
- The first ("cold") render of a page is 0–30 % slower than later ones; PDFKit keeps the parsed page.
- Render time grows roughly with the pixel count, so the heavy page costs about 50 ms per megapixel; the real cost of a deck depends on its content, not on its page count.

### Neighborhood fill: 20 pages at 4K

| Deck | Sequential, Mac | 4 tasks, Mac | Sequential, iPad sim | 4 tasks, iPad sim |
|---|---|---|---|---|
| Text fixture | 39 ms | 19 ms | 121 ms | 87 ms |
| Heavy pages | 6.98 s | 2.31 s | 7.62 s | 2.53 s |

The 4-task numbers include opening one `PDFDocument` per task. Parallel rendering with separate documents scales about 3× with 4 tasks.

### Memory

- **Bytes per image are exactly `width × height × 4`** (table above). With pixel buffers the test owns, the footprint grows by exactly that amount (20 images at 4K: 474.6 MiB computed, 475.3 MiB footprint, on Mac and in the simulator).
- **`CGImage`s from `CGContext.makeImage()` are not visible in the process footprint** on macOS or in the simulator: keeping 30 images at 6K (1.7 GiB computed) changed `phys_footprint`, `internal` and `resident_size` by less than 50 MiB, even after reading every image's pixel data. Core Graphics keeps that memory somewhere the task counters do not see (probably purgeable or IOSurface-backed storage). The memory is still used, so **the cache must count bytes itself** (`bytesPerRow × height`) and must not rely on the footprint. Whether iPadOS counts this memory against the app's jetsam limit can only be measured on a device (see below).
- **Missing autorelease pool:** on macOS, 60 discarded 4K renders without `autoreleasepool` grew the footprint by **1.4 GiB** until the test ended; with a pool around each render the growth was 0.5 MiB. PDFKit's drawing autoreleases objects that keep the bitmap alive. The simulator did not show this, but the production renderer must wrap every render in `autoreleasepool` on both platforms.
- The old app's worst case for comparison: count limit 200 at a 4K audience size is 200 × 23.7 MiB ≈ 4.6 GiB (plus presenter renditions), which is not acceptable on iPad and wasteful on Mac.

### Other observations

- Opening `large-deck.pdf` (320 pages) took 0.4–0.6 s on the Mac and 7 ms in the simulator in a second run; the first simulator run took minutes once (cold simulator file access, not reproducible). Opening is not a cache concern, but a production renderer should keep its worker documents open for the whole session instead of opening one per job.
- `os_proc_available_memory()` returns 0 in the simulator, so the iPad limit cannot be read there.

## Limits of these measurements

- **Simulator memory and timing are only indicative.** The simulator runs on the Mac's CPU, kernel and memory; it has no jetsam limit, and its GPU and memory bandwidth are the Mac's. Real iPads are slower and have a per-app memory limit of a few GiB, depending on the model.
- The heavy deck is synthetic. Real Beamer decks with large photos or many TikZ plots may be faster or slower; the text fixtures show the lower bound.
- Only one Mac was measured. Older or smaller Macs (8 GiB RAM) will render more slowly; 5K/6K displays are the expensive case.
- Displaying the images (SwiftUI `Image`, Core Animation upload) was not measured. It adds GPU memory per *visible* image, not per cached image.

## Real-device measurements still to take

Run the `RenderMeasurements` suite from the branch `prototype/render-cache-measurements` on a real iPad (Xcode › Test Navigator › `SlidePilotRenderingTests` › `RenderMeasurements`, destination: the iPad) and send the lines starting with `RENDERMEASURE` from the test log. Most useful:

1. **iPad (the oldest model that should be supported, and the iPad Pro):** render times, and `os_proc_available_memory` (the app's remaining memory limit).
2. **Whether `CGImage` memory counts against the jetsam limit:** compare the `os_proc_available_memory` lines that `retainedMemoryPerImage` logs before and while it keeps 30 images. If it drops by the computed bytes, the budget below is real; if not, the cache still has to count bytes, because memory pressure will reclaim or kill otherwise.
3. **Mac with an external 4K/5K/6K display** in a real presentation with the Xcode memory gauge open, to see the app's total memory with the proposed budget.
4. **One real lecture deck with photos/plots** (only the numbers, not the file) through `renderTimeHeavyPages`, to check whether the synthetic heavy deck is a realistic upper bound.

## Recommendation for the production cache

Approved and recorded in ADR 0005.

1. **One rendition per page and size class, not per view.** Key: (page, display mode/split half, pixel size bucket). The audience window and the presenter's "current" view usually show the same page; render once at the larger size and let the smaller view scale it down. Thumbnails get their own small cache (0.5 MiB each, rendered lazily as the sidebar scrolls).
2. **Priority order:** current page (audience size) → next page → previous page → further ahead. A navigation cancels queued neighborhood jobs that are no longer near the current page.
3. **Neighborhood:** current −1 … current +3 (5 pages). With text-like decks every page renders in under 10 ms even at 6K, so any neighborhood is enough; with heavy pages a single page can take 0.3–0.8 s, so pre-rendering the next 3 pages hides the delay for normal forward navigation. Jumps (overview, go to page) cannot be predicted and simply render on demand.
4. **Budget (bytes, counted by the cache):**
   - **macOS: 512 MiB** — the neighborhood plus about 3 recently visited pages at 6K (58 MiB each), or about 21 pages at 4K, or about 85 pages at 1080p.
   - **iPadOS: 192 MiB** — about 8 pages at the iPad Pro 13″'s own resolution, or 8 pages at 4K on an external display. Lower it to the neighborhood only on a memory warning.
   - Eviction: least recently used outside the neighborhood first; never evict the current or next page.
5. **Workers:** one renderer for the current/next page and up to two background workers, each with its own `PDFDocument` kept open for the session (≈3× faster neighborhood fills on heavy decks). Every render inside `autoreleasepool`.
6. **No pre-render on open** of the whole document or of the first 200 pages (old behavior); start with the neighborhood of the opened page.

## Re-running

The measurement suite is kept out of `main`. To re-run it, check out `prototype/render-cache-measurements` and run:

```sh
xcodebuild -project SlidePilot.xcodeproj -scheme SlidePilot -destination 'platform=macOS' -only-testing:SlidePilotRenderingTests/RenderMeasurements test
```

and search the log for `RENDERMEASURE`. Use an iPad simulator or a connected iPad as the destination for iPadOS numbers.
